# KinHub 0.1.0 — Note di rilascio

- **added / developer-experience**: Aggiunta una skill per trasformare analisi funzionale e architettura in feature autonome, tracciabili e ordinate per dipendenze e parallelismi sicuri.
- **added / platform**: Aggiunta la base full-stack di KinHub con API, PWA bilingue, temi, tutorial, guida contestuale, skill, infrastruttura Azure e pipeline.
- **changed / docs**: Consolidate nella ricerca KinHub e KinList le decisioni condivise su identita e inviti e quelle specifiche del servizio su paginazione, limiti batch, timer giornaliero, pipeline vocale e comportamento PWA.
- **added / shared**: KinHub ora permette di creare la prima famiglia da `/kinlist` con un solo nome, salvataggio atomico di famiglia e membership del creatore, endpoint dedicato e onboarding aggiornato.
- **added / backend**: Introdotto il catalogo persistito dei servizi familiari con KinList preconfigurato, disponibilita assegnata alle famiglie esistenti e nuove, Home dinamica basata sui servizi autorizzati e controllo server-side dell'accesso diretto a `/kinlist`.
- **added / frontend**: Aggiunta la route `/settings/family` con lettura del nome famiglia, pagine di membri attivi e inviti attivi, nuovi endpoint KinHub Family protetti e documentazione bilingue collegata.
- **added / frontend**: KinHub aggiunge la prima lista condivisa paginata di KinList con backend persistente minimo, cursori opachi, ordine stabile, categorie essenziali, autore e navigazione avanti/indietro senza cache locale dei dati.
- **added / docs**: Aggiunto il backlog esecutivo KinList con 13 feature autonome, tracciabilità completa, dipendenze, wave, gate e criteri verificabili.
- **changed / infrastructure**: Ristrutturata l'infrastruttura Azure con nomi dev espliciti, adozione incrementale e linked backend Static Web Apps. Sostituiti i workflow precedenti con CI, provisioning e release con action fissate a SHA.
- **changed / tooling**: Aggiornato l'harness con esecuzione autonoma delle feature fino alla Definition of Done, checkpoint riprendibili solo per soglia del contesto o human in the loop e consegna tramite pull request senza merge. Le GitHub Actions della PR devono essere tutte verdi sull'ultimo commit; ogni run rosso richiede diagnosi, correzione e nuovo push.
- **changed / documentation**: Introdotto nelle schede del backlog il frontmatter di avanzamento con una macchina a stati esplicita e completamento riservato a un comando della responsabile umana.
- **changed / architecture**: Documentata la pipeline HTTP Functions centralizzata e sicura per default, con Change Request FEAT-001, regole OpenTelemetry, convenzioni CR e reference skill validate dall'harness.
- **changed / backend**: Implementata la pipeline HTTP condivisa della Function App con correlation ID, Problem Details centralizzati, autorizzazione default-deny, route/OpenAPI condivise e telemetria worker basata su Azure Monitor OpenTelemetry.
- **changed / frontend**: Sposto l'help contestuale fuori dalle pagine, aggiorno il manuale utente e aggiungo nel menu Informazioni il link diretto alla guida introduttiva.
- **changed / tooling**: Rafforzato l'harness di implementazione e il prompt di bootstrap con guardrail anti-regressione derivati dai fix reali del repository: versioni/runtime Azure verificati, rename configurativi repository-wide, contratti workflow, Flex Consumption, storage identity-based, migration bundle, artefatti generati e verifiche live post-deploy.
- **changed / tools**: Esteso l'harness di implementazione a tutte le modifiche versionate del repository, inclusi fix, workflow e documentazione, rendendo obbligatori commit, push, pull request e monitoraggio delle GitHub Actions anche fuori dal backlog feature.
- **changed / tools**: Reso esplicito nell'harness che portare una feature a `In review` richiede sempre commit e push su `dev`, pull request aperta verso `main` e tutte le GitHub Actions verdi sull'ultimo SHA prima di considerare conclusa la consegna.
- **changed / backend**: KinHub ora crea o riusa un profilo applicativo da `(iss, oid)`, verifica la membership familiare attiva nel bootstrap post-login, espone la policy `Family` condivisa e mantiene offline soltanto la shell pubblica senza dati personali.
- **changed / backend**: FEAT-001 ora completa il percorso di accesso KinHub consumato da KinList, con contesto famiglia condiviso solo in memoria, test frontend mirati, guardrail repository-wide per route/OpenAPI Functions e deploy Azure PostgreSQL basato su Microsoft Entra e token identity-based per principal e migration.
- **changed / frontend**: La cache MSAL usa `sessionStorage` per mantenere la sessione della scheda durante il refresh. Il bootstrap famiglia resta obbligatorio e i dati applicativi continuano a vivere soltanto in memoria.
- **changed / tooling**: L'harness ora verifica che ogni route di una HTTP Function sia documentata in `openapi.yaml`, rendendo obbligatorio aggiornare il contratto statico con ogni nuovo endpoint.
- **changed / infra**: I merge su `main` distribuiscono automaticamente il solo scope modificato: il codice applicativo usa il deploy leggero, mentre infrastruttura e migration usano un percorso full-stack serializzato che applica il database prima del codice senza deploy duplicati.
- **changed / infra**: Separati i deploy Azure per responsabilita: `infra/**` esegue solo il provisioning Bicep, `src/backend/**` applica migration e distribuisce la Function App, `src/frontend/**` distribuisce soltanto la SPA, mantenendo l'ordine corretto nei commit misti.
- **changed / frontend**: Integro il design system condiviso nella shell e nelle route correnti, rimuovo la route demo, aggiungo validator e promuovo primitive, floating navigation e pattern ufficiali nella documentazione frontend.
- **fixed / infra**: Corretti i workflow di deploy per usare fallback compatibili con i secret e le variable gia presenti nell'environment `dev` e per derivare l'object id del principal OIDC dal token ARM invece che da lookup Graph fragile.
- **fixed / infra**: Corretto il workflow `deploy-infrastructure.yml` per risolvere in modo affidabile nome e object id dell'amministratore Entra di PostgreSQL, evitando parametri vuoti che invalidavano il deployment Bicep.
- **fixed / infra**: Corretti i workflow di deploy rendendo il build backend coerente con il percorso gia validato in `pr-quality` e sostituendo nel deploy frontend la discovery della Static Web App via `az staticwebapp` con query ARM generiche piu affidabili sul runner GitHub.
- **fixed / infra**: Corretto il bundle EF Core nei workflow di deploy usando la factory di design-time dell'Infrastructure invece di forzare la Function App come startup project.
- **fixed / infra**: Corretto il comando `dotnet ef migrations bundle` nei workflow di deploy rimuovendo l'argomento invalido `--self-contained false`, che interrompeva la generazione del bundle EF Core.
- **fixed / security**: La configurazione di Microsoft Entra External ID ora separa il tenant clienti dal tenant Azure e valida correttamente autorita CIAM, audience GUID e nome dello scope dei token API.
- **fixed / shared**: Allineati il testo di onboarding di KinList alla creazione famiglia gia disponibile e aggiunte verifiche PostgreSQL reali per migration FEAT-002, retry e concorrenza del repository.
- **fixed / infra**: Corrette le risorse Bicep per i deploy dev rimuovendo la app setting `FUNCTIONS_WORKER_RUNTIME` non valida per Azure Functions Flex Consumption e allineando il parametro del Key Vault alla purge protection gia abilitata.
- **fixed / infrastructure**: Corretto il runtime .NET 10 della Function App Flex per consentire l'allocazione dei worker ed evitare risposte 503 senza telemetria.
- **fixed / infra**: Corretto il deploy frontend usando `AZURE_FUNCTIONAPP_URL` come fallback autorevole per l'hostname API quando il provisioning infrastrutturale non viene eseguito nello stesso workflow.
- **fixed / infra**: Corretto il workflow di deploy frontend aggiungendo `AZURE_STATIC_WEB_APP_URL` come fallback autorevole per risolvere l'hostname della Static Web App quando nome e query ARM non sono sufficienti nell'environment GitHub.
- **fixed / backend**: Corretto il middleware di autorizzazione della Function App per risolvere i servizi scoped per-invocazione invece che dal costruttore singleton, con test di regressione che valida l'avvio del container DI con il middleware registrato.
- **fixed / backend**: Corretta la registrazione OpenTelemetry della Function App per non inizializzare l'exporter Azure Monitor quando `APPLICATIONINSIGHTS_CONNECTION_STRING` non e configurata, evitando il crash dell'host locale e coprendo il caso con un test di regressione.
- **fixed / backend**: Allineate le librerie Azure Functions Worker e gRPC alla versione richiesta dall'integrazione OpenTelemetry, rimossa una configurazione runtime non supportata, resa univoca la configurazione dello storage host con managed identity su Flex Consumption e neutralizzati i placeholder applicativi che causavano crash di bootstrap quando mancavano override ambientali.
- **fixed / backend**: KinHub ora usa un upsert atomico per il profilo applicativo `(iss, oid)`, tratta come indisponibilita del repository solo i guasti reali di persistenza e richiede una configurazione database esplicita tra `ConnectionString` locale e `ManagedIdentity`.
- **fixed / backend** ⚠️: Bootstrap, contesto famiglia, autorizzazione e telemetria condivisi usano ora nomenclatura e route KinHub; rimossi i contratti `/api/kinlist/bootstrap` e `/api/kinlist/family-context` attribuiti erroneamente al KinService.
- **fixed / infra**: Corretti i workflow di deploy per usare gli argomenti Azure CLI corretti nella gestione della firewall rule di PostgreSQL Flexible Server, distinguendo `--server-name` dal nome della regola.
- **fixed / infra**: Corretto il provisioning temporaneo delle firewall rule PostgreSQL nei workflow di deploy sostituendo il comando `az postgres flexible-server firewall-rule` con chiamate ARM via `az rest`, e reso affidabile il code deploy ricavando dinamicamente Function App, server, host e database direttamente dalle risorse Azure invece di dipendere da app setting o nomi statici.
- **fixed / frontend**: Rendo la pagina delle note di rilascio responsive sui dispositivi mobili e rimuovo la superficie card duplicata mantenendo una sola card per voce.
- **fixed / backend**: Risolto il test di telemetria che poteva fallire in modo intermittente durante l'esecuzione parallela dei test di integrazione.
